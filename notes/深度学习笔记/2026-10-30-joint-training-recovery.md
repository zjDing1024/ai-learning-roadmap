# 联合恢复：让索引进度与训练状态指向同一个安全点

日期：2026-10-30。本文为原创学习笔记，引用公开官方链接，不摘录或翻译第三方正文及代码。实际运行与交付结果见[当日日报](../../daily-learning/2026-10-30/README.md)。

## 先区分三种进度

索引流已经返回一批数据，只说明读取端推进了位置；完成反向传播，说明梯度计算已经发生；训练器完成必要更新并认可这一批，则又是另一个边界。把三个时点都称作“处理过”，会掩盖恢复时最关键的分歧。

例如先保存训练器，再多取一批后保存索引流，两份文件各自都可能格式合法，但索引流比模型状态领先。恢复后直接取下一批会跳过尚未训练的数据。反过来，若训练状态领先于索引流，重放旧批次可能重复计入梯度或再次更新参数。这是组件状态在时间上没有对齐，不一定是随机数本身出错。

本轮让 `JointTrainer` 独占全部训练状态。`step_microbatch()` 在调用索引流前就把安全标记设为假；索引流内部返回索引后，依次完成反向传播、必要的 SGD 更新与清零、必要的换轮，最后提交训练器元数据并恢复安全标记。调用方只有在整个方法成功返回后才拿到这批已提交索引。

| 时点 | 可能已经改变的状态 | 是否允许联合快照 |
|---|---|---|
| 初始化或前一批成功返回后 | 一致的模型、窗口与数据进度 | 允许 |
| fetch 后，`after_fetch` | 索引流游标已推进，训练器提交游标未推进 | 拒绝 |
| backward 后，`after_backward` | 本批梯度已写入 `.grad`，窗口元数据仍未提交 | 拒绝 |
| 更新后，`after_update` | 参数和 momentum 可能已经改变 | 拒绝 |
| `before_commit` | 可能已经清空窗口；尾批还可能准备了下一轮排列 | 拒绝 |
| 全部操作成功并提交后 | 游标、epoch、更新次数、窗口计数与模型状态一致 | 允许 |

参数校验在操作开始前完成；`after_update` 只用于会触发更新的一批。操作开始后的失败不会自动回滚，安全标记也不会在异常清理中恢复为真。旧对象不能继续训练或保存，必须重新加载一份先前成功保存的联合快照。即使失败发生在 SGD 已经修改参数之后，也不能只把游标退回去重试。

尾批固定保留，且在 epoch 结束时刷新未满窗口，再由索引流生成下一轮排列。尾批成功返回时的规范位置因此是下一 epoch 的游标零；快照中的 RNG 对应已经生成该排列之后的位置。本轮不开放 `drop_last=True`、空数据或外部可变模型接口。

最终几项元数据赋值、设置安全标记和返回并不是硬件原子指令。本项只对声明的方法边界及故障点建立约定，不承诺任意异步中断时的确认语义。

## 研究项目与源码观察

本轮重点项目为 [Hugging Face Accelerate](https://github.com/huggingface/accelerate)，由 Hugging Face 及项目贡献者维护。它组织 PyTorch 训练运行中的设备、执行与状态保存，当前借鉴的是“恢复所需状态不能漏项”的结构，而非直接引入完整训练框架。固定提交 `90b233c86202a5ded4bf66407e75222c5fb007fc` 的 [checkpointing.py](https://github.com/huggingface/accelerate/blob/90b233c86202a5ded4bf66407e75222c5fb007fc/src/accelerate/checkpointing.py)中，`save_accelerator_state` 分别处理模型、优化器、scheduler、符合条件的有状态数据加载器与 RNG 等组件。这个组织方式有助于列出状态清单，但分组件保存本身不证明这些状态来自同一训练提交点；本项目仍需独立定义安全点与失败语义。没有引入 Accelerate 运行时依赖。

数据读取侧继续对照 TorchData：

| 项目要素 | 阅读范围与当前阶段用途 |
|---|---|
| 项目与维护者 | [TorchData / meta-pytorch/data](https://github.com/meta-pytorch/data)，项目维护者与贡献者 |
| 解决的问题 | 为数据迭代提供可保存和可加载的进度，组织 sampler、dataset 与 iterator 的状态 |
| 固定版本入口 | v0.11.0 的 [stateful_dataloader.py](https://github.com/meta-pytorch/data/blob/377e64c1be69a9be6649d14c9e3664070323e464/torchdata/stateful_dataloader/stateful_dataloader.py) |
| 主要结构 | `torchdata/stateful_dataloader` 下的数据加载器、采样器与状态协议 |
| 适配原因 | 当前正在连接索引流与训练循环；先理解状态由谁持有，再决定哪些状态必须一起保存 |
| 可借鉴设计 | 显式状态接口、区分采样与数据状态、将不支持的运行条件写入恢复约定 |

所读 [StatefulDataLoader 源码](https://github.com/meta-pytorch/data/blob/377e64c1be69a9be6649d14c9e3664070323e464/torchdata/stateful_dataloader/stateful_dataloader.py)中，加载器的 `state_dict()` 委托给迭代器；单进程路径先获得索引，再从数据集取数据，保存时组织采样器、迭代器及数据集相关状态。这里能观察到读取组件的职责划分，不能据此推定模型已经完成反向传播或参数更新。

[官方说明](https://meta-pytorch.org/data/0.11/torchdata.stateful_dataloader.html)讨论了 worker 状态聚合，并明确不负责跨 rank 聚合。本项目仅研究公开接口与状态组织方式，没有使用 TorchData 运行时，也不实现这些并发功能。本轮“训练完成后才认可联合进度”的规则是本项目的受控设计，不把它写成上游实现的缺陷或额外保证。

## 联合快照必须回答的问题

| 状态类别 | 必须能回答的问题 | 遗漏后的风险 |
|---|---|---|
| 配置、数据身份、格式与运行时版本 | 恢复对象还是同一个实验吗？ | 相同索引指向不同数据，或按不同规则解释旧状态 |
| 当前排列与 epoch | 当前轮的访问顺序是什么？ | 只有游标不能确定下一条数据 |
| 已发出与已完成训练的进度关系 | 读取端是否领先，领先部分能否安全继续？ | 读过但没训练的批次被漏掉，或已计入的批次被重复处理 |
| 局部 CPU RNG 状态 | 未来排列从随机流哪个位置继续？ | 当前剩余序列相同，下一轮仍可能分歧 |
| 模型与 SGD 状态 | 参数以及 momentum 对应第几次已完成更新？ | 参数暂时相同，却在下一次更新分叉 |
| 待用原始梯度 | 哪些微批次已贡献梯度但尚未触发更新？ | 恢复时丢掉窗口前半段，或把同一贡献算两次 |
| 待用微批次、样本与目标元素计数 | 窗口何时结束，梯度应除以多少？ | 更新频率或尾窗口权重错误 |

本轮快照将索引流状态嵌入同一结构，同时保存 `epoch`、`cursor`、`updates`、`committed_batches`、`pending_batches/samples/elements`、模型、优化器与 `pending_gradients`。索引流内保存完整排列和局部 RNG；恢复端重新生成固定数据并核对摘要，同时核对内外游标、epoch 和窗口计数。外部期望配置应由调用方独立提供，不能从待加载文件照抄。

“联合”不只意味着把若干字典塞进同一个文件。字段之间应有可检查的关系：已完成批次数要与游标对应，待用计数要与窗口位置对应，空窗口不应带着旧梯度，当前数据身份要与重建数据一致。结构和摘要只能检查其中一部分：游标不一致的拼接状态可以被规则拒绝；若游标一致却换成另一份合法形状的旧模型，再重算摘要，格式本身未必能识别。完整性校验不能证明这些数值来自真实的同一次训练历史。

## 原始梯度和分母为什么要成对保存

设窗口中已经完成的微批次为集合 `W`，每批使用平方误差的求和损失 `L_b`。待用梯度与分母分别是：

\[
G_W=\sum_{b\in W}\nabla_\theta L_b,\qquad
D_W=\sum_{b\in W}\operatorname{numel}(y_b).
\]

窗口结束时，交给优化器的平均梯度才是 `G_W / D_W`。若输出有两个目标元素，`5+3` 个样本对应的分母是 `16`，不是 `8`，也不是微批次数 `2`。恢复时只有梯度没有分母，仍无法确定正确尺度；提前除以一个尚未确定的完整窗口大小，也可能把尾窗口处理错。

[PyTorch backward 官方文档](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.backward.html)说明多次反向传播会累积叶张量梯度。[Optimizer.state_dict 文档](https://docs.pytorch.org/docs/2.14/generated/torch.optim.Optimizer.state_dict.html)描述优化器内部状态与参数组；不能把这些状态当作叶张量待用 `.grad` 的替代。对本轮 SGD，momentum 属于已执行更新的历史，而原始梯度属于尚未结束的窗口，两者需要分开表示。[SGD 官方说明](https://docs.pytorch.org/docs/2.14/generated/torch.optim.SGD.html)给出了其更新语义。

## 当前排列和后续随机状态也要成对保存

当前排列已经生成，恢复其剩余部分不需要重新抽样；但下一 epoch 仍需要局部生成器的后续状态。因此恢复验证应跨越换轮边界。只恢复 seed 会回到某个起点，并不自动回到中断位置。[PyTorch Generator 官方接口](https://docs.pytorch.org/docs/2.14/generated/torch.Generator.html)区分 seed 与 `get_state()` / `set_state()`，这为本项目显式保存随机位置提供了基础。

本项目的固定前向不消耗训练随机数。这个简化有意把问题限制在数据顺序与累积状态上；它没有覆盖 Dropout、随机增强或多个随机消费者。添加任何一种新随机源，都应重新列出状态归属和调用时点，不能从本轮通过自动推断支持。

## 故障注入要证明什么

核心案例是：已经取得本批索引，训练尚未完成时故意失败。验收需要看到该批是否出现在读取侧、是否计入训练侧、失败后的对象允许什么操作，以及从先前合法快照恢复后最终发生什么。仅捕获一次异常，或者恢复后能够继续运行，都不足以证明训练轨迹正确。

对照应分别观察批次顺序和更新边界，再核对参数、momentum、待用梯度及计数。若只比较索引集合，顺序改变仍可能改变 SGD 轨迹；若只看最终 loss 接近，也可能掩盖中间发生过的遗漏或重复。故意让游标领先、遗漏待用梯度或重置局部 RNG，是帮助检验观察指标是否真的敏感的反例，不是要把所有伪造状态都变成解析错误。

这里描述的是验收目标，实际支持的切点、已运行案例和结果以日报及工程记录为准，不把计划清单写成已通过清单。

## 安全点、文件写入和 exactly-once 的不同范围

训练器返回成功、快照在内存中构造成功、文件写入成功，是三个不同事件。训练进度在内存中提交后，如果尚未保存就丢失进程，只能从更早的持久化快照继续，可能需要重新计算一段工作。失败前尝试过的计算，不保证物理上只执行一次。

本项目的验证目标是：在声明的固定条件和保存边界内，从可信联合快照恢复，得到与连续执行相同的受检训练轨迹。它不保证任意指令中断、外部副作用的事务一致性、文件系统断电持久性或分布式 exactly-once。保存失败也不能用未确认的新文件替代上一份可用快照。无论使用何种文件写入策略，都应单独说明它实际保证和没有验证的部分。
