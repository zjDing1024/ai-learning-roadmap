# 累积窗口内恢复：先定义状态，再比较轨迹

日期：2026-10-28。本文是独立学习笔记，不是上游代码摘录或翻译；工程结果见[当日日报](../../daily-learning/2026-10-28/README.md)。

## 问题从哪里来

上一日已经处理不等长微批次的归一化：窗口内先累积求和损失的梯度，到更新时再除以实际目标元素总数。若在一个窗口中途退出，模型参数仍是窗口开始时的参数，但进程已经完成了一部分计算。因此，“参数没有变化”并不意味着“没有新状态需要保存”。

设一个窗口已经处理两块数据，下一块尚未读取。此时继续训练所需的不仅是模型参数和 SGD 的动量，还包括前两块数据产生的原始梯度和、其实际目标元素数，以及下一块数据的位置。若只恢复参数与动量，却从第三块继续，前两块梯度会丢失；若保留梯度却从第一块重读，就会重复计入。两种错误都可能输出有限的 loss，不能只靠没有报错判断恢复正确。

## 研究对象与官方依据

选择 Hugging Face Accelerate，是因为它将模型、优化器、随机状态和数据读取进度作为真实训练工程问题处理，而不是只保存一组权重。研究固定版本 [checkpointing.py](https://github.com/huggingface/accelerate/blob/8c83b448d19f6356d4facd65c1d4763bf9fa51b2/src/accelerate/checkpointing.py) 与 [accelerator.py](https://github.com/huggingface/accelerate/blob/8c83b448d19f6356d4facd65c1d4763bf9fa51b2/src/accelerate/accelerator.py)，并结合[官方 checkpoint 指南](https://huggingface.co/docs/accelerate/usage_guides/checkpoint)。

在所阅读的常规保存路径中，训练状态涉及模型、优化器、scheduler、部分 sampler 或 stateful loader、scaler、step 与随机状态；没有看到单独保存参数待用梯度的步骤。由此得到的是本项目的研究判断：不能因为接口叫“保存训练状态”，就认定它自动满足任意未结束累积窗口的恢复约定。这不是对上游所有配置的完整审计，也不是上游存在缺陷的结论。

[PyTorch Module.state_dict 文档](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Module.html#torch.nn.Module.state_dict)说明其内容为参数和持久 buffer，并说明返回内容的浅引用性质。因此，模型状态不等于待用梯度，保存快照还需避免继续训练改变所持有的张量引用。[Optimizer.state_dict 文档](https://docs.pytorch.org/docs/2.14/generated/torch.optim.Optimizer.state_dict.html)说明恢复时按参数组顺序配对状态且不会额外核实身份；本项目不能把名称、形状、顺序等一致性检查交给一个过于宽泛的“加载成功”判断。

## 原创实现的最小状态约定

本次将可保存位置限定为一个微批次的前向与反向已完成之后，且没有正在执行的参数更新。快照可能处于尚有待用梯度的窗口内部，也可能处于已经清空梯度的更新边界。它不是任意 Python 指令位置、反向传播中途或优化器更新中途的故障恢复承诺。

状态约定至少要回答五类问题：

1. **接着用哪套参数更新？** 模型参数、SGD 状态和参数身份要一致。
2. **还有哪些贡献没有应用？** 保存未归一化的梯度和，区分“没有待用梯度”与数值为零的梯度。
3. **下一次更新除以什么？** 保存实际目标元素数，并记录样本数和微批次计数，不能拿固定窗口上限代替尾窗口真实分母。
4. **下一块数据是什么？** 保存固定顺序数据游标、epoch 和更新计数，避免遗漏或重复。
5. **还是同一个问题吗？** 用版本、配置、数据指纹和结构约束拒绝与当前约定不匹配的输入，而不是勉强接着跑。

在本次确定性 fixture 中，数据顺序固定且模型没有随机前向；恢复后的训练没有正在消耗的采样随机流。这只是主动缩小验证面，不表示随机状态对一般训练不重要。若扩展到 shuffle、Dropout 或多 worker 预取，必须另行定义随机状态和数据流的可恢复边界。

## 怎样验收才有意义

连续运行是基准；恢复运行从同一 fixture、配置和初始条件出发，在声明的安全点保存，交给新进程继续。比较不应只看最终 loss，还应覆盖后续参数、动量、更新次数和数据进度。优先检查窗口内部、完整更新边界、不完整末窗口和 epoch 边界，具体执行覆盖以日报和工程结果文件为准。

故意删除或修改状态，可以帮助检验加载器是否拒绝明显不一致的快照；但“schema 校验通过”“文件摘要一致”和“训练轨迹一致”是不同层次的证据。摘要不是身份认证，有限值检查也不是沙箱。本项目只面向自己生成且可信的训练快照，不加载陌生文件来证明安全性，不据此承诺应对恶意 pickle 或一般不可信输入。
