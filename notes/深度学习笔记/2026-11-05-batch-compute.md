# Wine 批次预算与 CPU 计时边界

## 研究项目与来源

项目：[PyTorch](https://github.com/pytorch/pytorch)，由 PyTorch 团队及社区维护。本次研究的是 `torch/utils/benchmark/utils/timer.py`：它在通用计时器之上处理预热、线程数、重复测量和必要的加速器同步，并以测量对象承载环境信息。适合当前阶段的价值不是再引入一套框架，而是把“执行了多少训练”与“测量了哪一段时间”分开。

- [固定官方源码](https://github.com/pytorch/pytorch/blob/5c4886908584029761b579af026dcfb627c84070/torch/utils/benchmark/utils/timer.py)
- [版本 2.14 Benchmark Utils 文档](https://docs.pytorch.org/docs/2.14/benchmark_utils.html)
- [官方 BSD-style 许可证](https://github.com/pytorch/pytorch/blob/5c4886908584029761b579af026dcfb627c84070/LICENSE)
- [Python 3.12 time 文档](https://docs.python.org/3.12/library/time.html)

本次代码为原创，不复制上游实现，也没有声称使用 `torch.utils.benchmark.Timer` 或其自适应重复算法。我们固定三次测量，以可审计的训练成本换取较窄的结论；不把它当作正式性能排行榜。上游源码固定提交不代表安装包全部源码身份相同；实验实际版本单独记录。

## 借鉴的设计与主动限制

先预热并固定单线程，可减少部分初始化差异；重复测量仍会受共享宿主调度影响。我们轮换三种训练分支的执行位置，减轻始终先跑同一分支的顺序混杂，但没有证明噪声被消除。三个同进程重复只给出描述性范围，不足以报告置信区间或稳定加速比。

`perf_counter_ns` 衡量经过时间，`process_time_ns` 衡量进程消耗的 CPU 时间；两者的差值含义不同，不能简单叫作同一“训练耗时”。本实验仅 CPU，不对 GPU 异步执行作结论。`ns` 是返回单位，不代表纳秒级实际分辨率，时钟能力另行记录。

## 原创实验合同

沿用已公开 batch16/32 的三个唯一分支、相同初始化与四轮显式索引排列。每模型／seed 的参考、预热和正式测量都重新构造模型，不在前一次训练后的权重上接着跑。计时包含 prepared batches 上的 Python 循环、zero_grad、forward、CE、backward、SGD.step；排除导入、初始化、索引准备、评估、哈希和参考验证。两次计时器调用也有开销，没有虚构扣除它。

去掉审计哈希的计时循环，需与原审计训练器比较最终张量、完整训练 CE 和实际行顺序。检查通过回答“测量路径是否保留训练结果”，而不是“谁更快”。不同预算的训练结果本来可能不同，不得要求它们互相相等。

18 次参考 + 18 次预热 + 54 次正式测量 = 90 条实际轨迹，总计 1080 更新、24390 训练访问；90 次终点训练集评估另计 9630 访问。不能只报正式测量成本。测试及交付中的重复执行另有成本，不混入主 JSON 的单次预算。

## 能力价值与后续

这项记录可以展示 AI/ML Engineer 的计量边界、非干扰验证、预算核算与谨慎的性能解释。当前不覆盖端到端数据加载、GPU、AMP、分布式或用户独立操作能力。巩固练习是指出为什么同样十四次更新不代表相同时间，为什么去掉逐步哈希后仍须验证最终参数。

既有路线中的 update-clock scheduler 候选保留；本轮先补齐成本计量，是针对上一项“两个预算都不等计算成本”的缺口，不重复更换 batch size 搜索好看的排名。
